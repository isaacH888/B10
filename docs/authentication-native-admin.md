# Native administrator password and TOTP

The primary `/admin/login` page uses Cognito's public `USER_AUTH` API with a preferred `PASSWORD` challenge. The backend submits `PASSWORD` together with `PREFERRED_CHALLENGE=PASSWORD` over verified HTTPS, observes the resulting required native challenge, and follows only the expected native challenges. AWS operator credentials are not involved. Customers retain managed email/password and Google login in their separate pool; administrator Google is disabled.

## Why managed login failed

The protected record for request `2407f08818ac45318995a085b6e45417` contains `mfa_assurance_missing`: both ID and access tokens lacked `acr` and `amr`. The new development pool was inspected read-only and confirmed Plus, mandatory TOTP, password-only first factors, COGNITO-only provider, token rotation and the exact approved native owner. Cognito's protected authentication events recorded successful password and MFA challenges. The user also confirmed entering an existing authenticator code.

The requested ACR and freshness parameters reached Cognito, but the returned signed claims did not establish the required assurance. The precise service-side reason for their absence is not established. No pool reset, factor reset, account deletion, or synthetic claim is a remedy in this change. The retained OAuth callback continues to require its original signed ACR/AMR, nonce, PKCE, state and freshness checks. The new flow uses a different explicit proof: the backend itself receives successful completion of `SOFTWARE_TOKEN_MFA` for the browser-bound Cognito challenge. [AWS native challenge API](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_RespondToAuthChallenge.html).

## Sign-in and initial setup

1. An approved existing administrator opens `/admin/login` and clicks **Continue with password** to open the sign-in form. They enter their team email and password, then submit the six-digit authenticator code. The short-lived native transaction starts after that click. The dashboard opens only after the backend accepts the native challenge result and the frontend reads the resulting protected session.
2. An invited administrator uses the temporary password received privately from Cognito. `NEW_PASSWORD_REQUIRED` asks them to choose a new password. Existing approved attributes remain fixed; the page cannot change the account's identity or role.
3. If Cognito returns `MFA_SETUP`, the page shows the account's enrollment key. Add it manually to a trusted authenticator as a time-based, six-digit account, then enter a generated code. The key is shown only to that browser over the authenticated setup transaction; it is not sent to a QR service, URL, browser storage or logs.
4. Successful enrollment completes Cognito's setup challenge but grants no application session. Enter the new password again and complete a subsequent `SOFTWARE_TOKEN_MFA` challenge. Use a new authenticator code if the preceding one has already been consumed.
5. Wrong codes, expired or consumed transactions and unexpected challenge types require restarting password sign-in. Password/TOTP setup alone, a pool setting, a configured authenticator, an email match or tokens returned before the expected MFA challenge never authorize the dashboard.

The browser exchanges only ordinary form data and the opaque HttpOnly transaction cookie with the same-origin backend. Cognito requires the password in this preferred-password initiation, rather than returning an empty password prompt. Native choice discovery against the live client was verified without submitting a password: it returned `SELECT_CHALLENGE` with `PASSWORD` available and no tokens. The subsequent account-holder retry completed real native password/TOTP sign-in and opened the dashboard, corroborated by a protected native completion record. Other live verification below remains required. [AWS choice-based password request](https://docs.aws.amazon.com/cognito/latest/developerguide/amazon-cognito-user-pools-authentication-flow-methods.html).

The runtime holds passwords/codes only for the current request and never persists them. Cognito challenge sessions, provider tokens and enrollment keys are encrypted before database storage. Sensitive responses are `Cache-Control: no-store`; production must use HTTPS. No client secrets or provider tokens are returned to JavaScript. [AWS TOTP association](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_AssociateSoftwareToken.html), [AWS enrollment verification](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_VerifySoftwareToken.html).

## Transactions and authorization

`GET /api/v1/admin/password/transaction` starts or resumes a browser-bound transaction and returns its step, expiration and CSRF token. `POST` to that path submits the fields required by the current step, with the exact configured `Origin` and `X-CSRF-Token`. `DELETE` cancels it with the same protections. The native cookie uses HttpOnly, SameSite=Strict and Secure in hosted environments. Each successful transition rotates its opaque credential; an attempt consumes the prior transaction before provider I/O. The original five-minute deadline is fixed and no more than five transitions are accepted. Invalid or repeated submissions cannot reuse the Cognito session. Login and challenge requests are rate limited.

The supplied email selects exactly one active approved native identity in the configured admin issuer. It grants nothing. Authentication targets that identity's stable Cognito subject, which is the canonical username in the provisioned email-username pool. The final signed ID/access tokens must bind the same subject, issuer and app client, valid signatures, expiration, required scope, verified email and fresh authentication time. Historical Google aliases and foreign issuer subjects cannot inherit a native grant. Access and role are rechecked before enrollment, at completion and while creating the session.

The server session records the explicit `cognito_native_challenge` proof and completion time; it never fabricates `acr` or `amr`. MySQL version projections are normalized to integers before encrypted JSON serialization. A persistent per-identity login version fences native transactions across operator revocation, role changes, disable and recovery, including provider calls already in flight. The native session requires the original approved version. Sensitive actions require MFA completion within five minutes. Session limits remain eight hours absolute and fifteen minutes idle; polling does not renew idle expiration.

Native refresh uses the public `GetTokensFromRefreshToken` API with the confidential app-client secret and rotating refresh token, without IAM. Refreshed signatures, issuer/client/subject and original signed authentication time are checked again; refresh cannot manufacture or renew MFA proof. Current-user/factor checks detect provider disable, sign-out and lost registration, and local grants/version are checked after provider I/O. Logout cancels pending native/OAuth flows, revokes local access immediately and attempts provider token revocation. Existing protected role checks and audited private recovery remain in force. [AWS rotating refresh API](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_GetTokensFromRefreshToken.html).

## AWS configuration and release

No AWS resources or live users are modified by this implementation. Do not recreate the pool or owner. Read-only inspection of the fresh stack confirmed its client already enables `ALLOW_USER_AUTH`; native authentication therefore needs no new authentication-flow permission. The template additionally sets `AdminClient.AuthSessionValidity: 5` to align Cognito's challenge lifetime with the application transaction. The inspected live client currently uses three minutes, which remains safe but can expire a setup challenge sooner.

For a separately authorized release:

1. In the existing admin pool/client, retain `ExplicitAuthFlows: [ALLOW_USER_AUTH]`, `SupportedIdentityProviders: [COGNITO]`, generated secret, `PreventUserExistenceErrors: ENABLED`, `EnableTokenRevocation: true`, refresh rotation, five-minute ID/access tokens, eight-hour refresh tokens, and readable `email`, `email_verified`, `name`. Retain Plus, required SOFTWARE_TOKEN_MFA only, password-only first factor and no remembered-device configuration. Do not enable `ALLOW_ADMIN_USER_PASSWORD_AUTH`, custom auth, remembered-device bypass, or `ALLOW_REFRESH_TOKEN_AUTH`.
2. Review a CloudFormation change set for `infra/cognito-authentication.json` against the existing stack with its existing parameter values and `CAPABILITY_IAM`. The intended new client setting is `AuthSessionValidity: 5`; no pool/client replacement, user deletion, IAM expansion or customer-provider change is required. Stop if the change set proposes replacement or unrelated drift. Alternatively, set the existing app client's authentication session duration to five minutes in the Cognito console, then reconcile that setting through the normal infrastructure process. Do not execute either change during this fix.
3. Preserve the customer Google provider and its existing Google OAuth redirect. This flow uses no administrator Google redirect or Google secret. Preserve the admin OAuth callback/logout URLs for the retained strict route.
4. Export the corresponding existing issuer/client ID/client secret into private backend configuration. Do not export operator AWS keys or attach `AdminOperatorPolicy` to the web service. The native API requires public client-secret calls, not `AdminInitiateAuth` or `AdminRespondToAuthChallenge` IAM permissions. [AWS authentication API authorization](https://docs.aws.amazon.com/cognito-user-identity-pools/latest/APIReference/API_InitiateAuth.html).
5. Apply additive migrations through the migration environment: from `backend/`, run `.venv/bin/python -m app.migrations`. Previously applied migrations 0001-0003 remain unchanged; 0004 introduces per-identity native-login revocation versions. Grant the runtime `SELECT` on `auth_admin_login_epochs` and the private operator `SELECT`/`INSERT`/`UPDATE`, along with `SELECT`/`INSERT`/`DELETE` on `auth_admin_native_flows` and its existing session/identity/audit privileges. DDL belongs to the migration process. Restart the backend and serve the built frontend through the same origin.
6. For a new approved administrator only, verify identity privately and use the existing operator `bootstrap-owner` or `invite-admin` procedure. An already approved owner needs no reprovisioning. Lost-factor recovery remains the private verified `recover-admin` command, never a public reset endpoint.
